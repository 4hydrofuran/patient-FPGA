# 任务 6：无模型完整流程验收

本任务验证“文字问诊 → 检查后交付 → 状态与取消 → 冻结记录 → 主任评价 → 新问诊”。回答来自合成病例的规则句，主任总结来自评分模板，全程不需要模型或联网服务。

本机结论：**规则演示模式下完整软件流程通过**。这不代表真实模型、KV260、实体触摸、屏幕键盘、语音或 PL 已通过验收。当前案例与评分仍待教师审核。

## 一次命令复跑

在 `web_gateway` 目录执行（输出文件名必须是新的）：

```powershell
.\.venv\Scripts\python.exe -m patient_web.workflow_acceptance --output docs/acceptance/my-workflow.json
```

程序自动在空闲回环端口启动独立规则服务，执行真实 HTTP/SSE 检查，再停止该服务。在同一地址建立一个新应用实例，检查 instance_id 改变、记录为空、旧会话返回 404。所有自建服务随后关闭，不调用当前预览中的用户会话。

输出 `PASS_DEMO_WORKFLOW` 和逐项 JSON 证据；失败时输出 `FAILED`，退出码为 2，保留失败项。默认全部通过时共 64 项检查（包括准备条件）；详细场景见下表。这是本机服务实例重启检查，不是 KV260 断电重启测试。

也可以指定一个刚启动、还没有任何会话的专用联调服务：

```powershell
.\.venv\Scripts\python.exe -m patient_web.workflow_acceptance --base-url http://127.0.0.1:8769 --output docs/acceptance/my-external-workflow.json
```

指定外部服务时只允许回环地址，必须是显式 `demo + demo-lab`。检测到任何已有会话便拒绝开始，不替用户关闭问诊；仅收尾自己建立的测试会话。外部服务的重启标为 `NOT_TESTED_EXTERNAL_SERVICE`，程序不会停止它。每次验收建立 3 个会话；服务原有 8 会话容量限制保持不变，所以复跑宜使用默认独立服务。

“模拟失败”会在服务日志产生预期错误记录；以报告的断言与最终 verdict 判断测试是否通过。

## 手动观察页面

在独立端口启动：

```powershell
.\.venv\Scripts\python.exe -m patient_web --backend demo --demo-lab --port 8769
```

同时打开问诊页面 `http://127.0.0.1:8769/` 和联调控制页 `http://127.0.0.1:8769/lab`。

联调页设置“下一轮场景”，点“应用到下一轮”，再到问诊页面提问。设置仅消耗一次，之后恢复正常。延迟、超时、失败可等待 0.2–10 秒，默认 3 秒。延迟会刻意等待结束后再返回，以验证取消后的旧结果确实被屏蔽。错误事实候选固定为“每次疼痛持续99分钟。”，不允许输入任意候选或改动病例。

澄清、策略拒绝等提问可能直接走模板，不进入回答模块。这类问题也会消耗当前选择，联调页会明确记录 `adapter_invoked=false, injection=null`，不能将它当成故障测试成功。

| 场景 | 操作 | 应得到的结果 |
|---|---|---|
| 正常三轮 | 病例 1，依次问“哪里疼？”“每次疼痛持续多久？”“不是没有呼吸困难吗？” | 前两轮分别回答胸骨后、10 分钟；第三轮澄清；结束后 20 分、2 项覆盖、1 条待复核 |
| 评分依据 | 结束后查看评分依据、待复核、问诊记录 | 引用第 1、2 问；待复核保留第 3 问原文；主任总结与分项一致 |
| 等待与重复操作 | 选择延迟场景，提交持续时间问题 | 回答尚未显示；输入、发送和结束禁用，取消可用；接口重试同 ID 不生成第二轮 |
| 取消 | 延迟期间点取消 | 先显示取消收尾，保持忙碌；等待结束后没有患者回答，恢复操作 |
| 错误事实 | 选择错误事实，问“每次疼痛持续多久？” | 不显示 99 分钟，发布检查通过的 10 分钟模板 |
| 模拟超时 | 选择超时，问持续时间 | 发布检查通过的模板，来源 `TEMPLATE`，`model_called=false` |
| 模拟失败 | 选择失败，问持续时间 | 本轮失败，明确提示没有发布回答；无回执；下一轮可正常完成 |
| 刷新 | 正常问诊后或评价后刷新 | 同一服务实例内恢复记录与冻结评价，不重复生成 |
| 新病例 | 结束后选择病例 2，开始新问诊 | 记录为空，之前评价保持不变 |
| 空问诊 | 不提问直接结束 | 0 分、10 项未覆盖、0 次提问，模板总结可读 |
| 长记录 | 多次提问并滚动、切换页签 | 文字区可滚动，1024×600 下主要操作不被挤出屏幕 |
| 重启服务 | 仅在自建测试服务上验证 | 新 instance_id、旧会话失效，不声称永久保存记录 |

取消和失败不一定撤销得分：原评分按已接收的医生提问计分。患者上下文只包含成功发布的回答，两者独立。包含取消的故障问诊得到 20 分是预期行为，不能据此认定迟到回答已发布。

## 标记和接口边界

- 默认服务没有联调页、脚本或故障控制接口，访问返回 404。只有 `--backend demo --demo-lab` 才启用；native 与该选项组合启动报错。
- `GET /ui/v1/status` 的 `demo_lab` 表示是否开启联调，主页面同时显示联调标记。
- `GET /ui/v1/demo-lab` 查询待执行场景、当前场景和最近 20 轮诊断。
- `POST /ui/v1/demo-lab` 设置 `{ "scenario": "delayed", "delay_s": 3.0 }`。合法场景为 `normal / delayed / wrong_fact / timeout / failure`；忙碌时返回 409，当前轮不能被中途修改。
- 故障选择和诊断不改变文字交付回执、评分或评价结构。候选文字不进入公开快照或 SSE。
- 规则正常回答来源为 `DEMO_RULE`，模板回退为 `TEMPLATE`。模拟超时的注入记录保存在联调诊断中，不能使用要求真实模型调用的 `TIMEOUT` 回执。真实 native 的 `TIMEOUT` 语义保持原样。
- 延迟期间发出实际的 `response.preparing`；不伪造 `generation.started`、真实推理耗时或硬件执行。纯文字页也不宣称已播音或用户已读。
- 场景选择和会话仍只存在内存，进程重启会清空。单活动任务、无等待队列等原限制保持不变。

## KV260 连接后的待验清单

当前板子未连接，以下全部标为 **NOT_TESTED**。现场操作人逐项记录系统/浏览器版本、日期、截图和结果，不提前勾选通过。

1. 核对 Ubuntu 版本、ARM64 架构和 Python 版本；当前包要求 Python ≥3.12。为板端单建虚拟环境、安装适配 ARM64 的依赖，不复制 Windows `.venv`；若版本不兼容，先解决运行环境再验收。
2. 将交接包解压到独立目录，启动 demo-lab，板上浏览器访问本机回环地址。页面不依赖外部 CDN；依赖安装所需软件包须事先准备。
3. 在板上运行同一个自动验收命令，保存新的 JSON 报告。服务只运行在 PS/Linux 侧，无需 PL 或模型。
4. 确认 HDMI 实际输出为 1024×600 横屏；观察字体、背景、主任图片和长内容滚动。
5. 用实体触摸完成发送、取消、结束、四页签切换和新问诊，检查点击位置与误触。
6. 打开屏幕键盘实际输入；检查输入框、发送按钮是否可见，收起键盘后布局是否恢复。浏览器缩小窗口的结果不能代替此项。
7. 反复练习并刷新，确认没有串病例、卡死；仅在测试会话上重启服务，确认旧记录清空并有提示。
8. 真正模型接入、模型超时后的原生进程隔离、回答质量、性能、语音和 PL 另行联合验收，沿用 `MODEL_HANDOFF.md`。本次演示失败后能恢复，不能证明真实模型故障后一定可恢复。

供现场填写的结构化待验项见 `acceptance/board-workflow-checklist.json`。
