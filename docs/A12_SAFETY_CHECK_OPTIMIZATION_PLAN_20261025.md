## 1. 建议采用的路线

优先减少两类时间：**整个验收窗口的重复取证时间**，以及**普通请求每个投影的管理等待时间**。分别计时，分别验收。

推荐顺序：

1. 先用无重型诊断的普通 R0/hit 请求探测真实资源包络；将完整数值取证、电脑核对和最终性能窗口分开，同一固定版本的有效证据按适用范围复用。
2. 将普通模式逐投影同步日志改为请求边界持久化，先保留逐投影 IPC 和新鲜检查，单独测收益。
3. 将静态身份核验移到启动/重配置边界，健康观测集中到有界周期；投影仅检查新鲜快照和本地状态。
4. 先试每个物理微批一次许可，再评估每请求一次有界许可。正式使用选择已通过验证的粒度。

前三项的主要改动位于 A 的编排和管理代码。**本轮保持 B 的接收源码、HLS 核、公共数学/ABI、微批上限和数值标准不变。**

## 3. B 的 PL 实现决定了哪些检查不能省

当前选择 B 来源 commit `e227297ee1bb0bdf542fc81761642b23639e15c0`、double 变体、build `0xB3030002`。所选核的 `T<=8`、`N/K<=4864`；公共软件契约与 B 私有 KernelMeta 是两个层次。

[核头文件](C:/Patientqwen/hw/linear_B_received/B03-supplement-e227297-20261003/payload/src/w4a8_linear_v1.hpp:49) 的 KernelMeta 为 40 字节；A 端使用 64 字节传输区。每次提交前 A 清零 meta，B 完成后写 magic/build/job/status/done/count/algorithm_weight_bytes；[主机核验](C:/Patientqwen/modules/linear_A/xrt/host_contract.cpp:64) 检查它们。

因此：

1. **许可可分组，硬件完成必须逐投影确认。** 一份微批许可覆盖 72 次投影，不意味着只需一次 XRT 完成或一份 meta。
2. 保留输入同步、meta 清零与同步、ERT 完成/错误状态、meta 回读核验、Y 同步、有限值与 padding 检查。`done=1` 本身不代表成功。
3. 当前 count 是“主机 seed=0 后，核成功写回 1”的逐调用证据；不是独立累计硬件计数器。主机预算、成功次数、原始 meta 和许可次数分别记录，不能互相冒充。
4. 所选 [B 核](C:/Patientqwen/hw/linear_B_received/B03-supplement-e227297-20261003/payload/src/w4a8_prefill_v1.cpp:519) 仍逐调用检查 ABI、维度、长度、指针和 W4 保留码。它与主机加载检查处于不同边界；本计划不把它们认作可直接删除的重复代码。
5. 核超时或 start 抛错不证明 DMA 已停止。保留 POISONED、禁止消费失败输出、禁止新提交及所有权保留。不得因租约到期自动释放 BO/锁或启动第二个 worker。

XRT 官方流程同样要求先同步输入，再执行并等待完成，最后同步输出；此处只引用 API 顺序，实际兼容性以项目固定 XRT 2.18.0 和受测源码为准，不用网页版本替换工具链。[XRT Native APIs](https://xilinx.github.io/XRT/2024.1/html/xrt_native_apis.html)

具体调整：

- 普通资源探测、数值窗口和最终性能窗口分开，避免先生成/重读约 1.136 GiB 原件再测普通应用。资源探测先给出普通路径结果；数值门禁成功后才开启最终性能验收。
- 全量读取时一次完成 SHA、逐字节对照及 manifest 字段；不再为 FILE_HASHES 和独立分析无差别多扫同一组文件。损坏、截断、文件替换、尾块和旧格式缺字段继续严格拒绝或明确 NOT_AVAILABLE。
- 如继续采用现有流式读取候选，先完成其当前 tip 的无板验证；这项诊断修复不作为普通资源探测的前置。原件可在确认所有提交完成、正常关闭且设备已安全释放后继续在电脑离线核对；若关闭/释放未知则保持隔离。比较晚做不能变成不做，也不能先宣告数值 PASS。
- 对已经完成且身份稳定的诊断文件，在同一 FD 的读取后给出 DONTNEED 建议并观测实际 CMA；不碰模型 mmap 页，不执行全局 drop_caches，不删除旧证据。DONTNEED 是回收建议，不能把返回成功视为已释放物理页。[Linux posix_fadvise 文档](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html)
- 每窗口保存一份环境/制品身份、每请求一份汇总，其他记录引用它们。历史治理文档每阶段汇总更新一次；故障立即登记，不在每个投影复制同一套状态文件。

## 6. 日志与许可协议设计

### 6.1 第一轮仅改变持久化粒度

普通请求 BEGIN 记录：request_id、模式、程序/模型/核/契约/输入身份、实例代次、准入快照、预算、期限。同步持久化成功后，才允许该请求进入任何 PL 提交。

运行中只更新固定容量内存摘要与环形明细，持续累计 attempted / started / completed / validated / failed / unused_budget 等有明确来源的计数。满时覆盖明细并增加丢弃计数，不能转为无界列表或隐式逐投影写盘。这里的计数名称是建议字段，不代表现有硬件新增了计数能力。

END 汇总实际结果、状态清理、计数、健康范围及错误。完成同步持久化后再交付最终答案；首次创建日志文件/目录仍处理目录持久性。BEGIN 失败不启动，END 失败返回审计失败并阻止下一请求，不能通过再次计算来补记录。故障日志的持久化尽力执行，但持久化失败不能阻止先停止新提交。

**这是证据语义变化：掉电后可能只有“请求曾被授权”，没有最后一个投影的位置。** 未完成请求恢复时按执行状态未知处理，旧授权作废，先确认设备状态，禁止自动重放。严格模式保留逐许可持久证据。常规请求许可日志同步趋近 BEGIN/END 两次，生命周期、拒绝和异常仍可另有持久记录，不承诺全服务只有两次 fsync。[Linux fsync 文档](https://man7.org/linux/man-pages/man2/fsync.2.html)

### 6.2 周期健康与边界检查

复用已有 HealthSchedule / kmsg reader，不增加独立大服务。健康快照至少包含采样时间、有效期、序号、故障锁存与资源值；原子发布一致快照，投影在启动前读一次。周期监控不能被许可循环、慢磁盘或完整诊断比较长期阻塞。

采样周期和最大新鲜度须以现有故障响应要求确定；附件的“1 秒/3 秒”仅作试验候选，当前不视为安全参数。记录从故障产生到禁止下一次启动的最大观测延迟；新鲜度超限即拒绝，不允许无限用最后一份健康结果。XRT 报错、ERT 异常和 meta 不匹配立即锁存，不等周期采样。

最新共享记录中的 soft-lockup 提醒：用户态监控不能保证解决内核卡死。监控或 worker 无调度、在途设备状态未知时，不宣称撤销已经生效，不移交设备，也不自动复位。

### 6.3 授权粒度逐步扩大

先保留轻量逐投影 IPC，确认迁移检查无遗漏后，再试微批授权：

- 绑定 manager/worker 实例、设备代次、请求 ID、模型/配置上下文、允许阶段、job 范围、微批编号、提交预算和单调 deadline。
- 24 层每层 gate/up/down 共 72 投影；prefill 预算由真实执行图核对 `72×ceil(N_new/8)`。decode 按实际后续 decode 调用数，每轮 72；首输出 token 可由 prefill logits 得到，不能机械多加一轮。warm、R0、hit、尾块分别计算。
- 本地权威预算放在实际启动核的后端入口，所有启动路径都经过它。router/backend 独立 DSO 的静态序号不能误当共享授权计数；不能复制出两份各可用满额的额度。
- 在 run.start 前再检查取消/故障/代次/期限并扣启动额度；区分“许可已发”“启动尝试”“完成验证”。已尝试启动但结果未知时额度不返还，不自动重试。
- EOS、取消和请求结束销毁未用额度。manager 失联/重启、worker 重启、设备重配使旧授权不可再用。撤销与启动竞争必须有明确串行化点；竞争前已获准的在途提交保留完成/隔离语义，不能承诺远程取消瞬时中止 DMA。

旧 107/37-token 的 prefill 许可往返可由 1008/360 次变为 14/5 次；**实际 PL 提交仍为 1008/360 次**，warm 和 decode 另计。这是设计上的次数变化，尚未实现或测得。

只有受控单 worker 的本地执行约束、失联、撤销及恢复均通过时，才评估整请求授权。把裁决放进 worker 会减少管理器逐投影的独立裁决，不能声称隔离保证完全不变；worker 不可信或无法可靠撤销时，停留在轻量逐投影/微批模式。当前不将请求级授权列为默认验收前提。

## 8. 测试与性能验收

### 8.1 按影响选择验证

每个候选先跑历史契约保护，再跑新版配置校验及相关测试。公共 contracts/fixtures 保持字节不变。测试层级分别记录；PC 控制替身不能证明真实在途 DMA 可释放。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 固定输入 R0、warm+hit、尾块、连续两请求/换病例 | 输出 token、logits 和必要混合状态满足原标准；活动状态清理；前缀身份一致；内容检查通过 |
| 重复/越序 job、错误 lane、超预算、错误阶段、旧代次 | 在核启动前拒绝，无旧结果可消费；预算不因拒绝/重试被重置 |
| 取消、EOS、过期、manager 断连、监控停摆 | 不再放行新提交；剩余额度作废；在途提交按完成或隔离处理 |
| worker/manager 重启、设备重配、第二访问者 | 旧授权失效；双锁及统一访问协议保持排他；未知设备状态不可移交 |
| 内存/BO 失败、温度告警、kmsg 丢序、ERT/同步异常、错 meta | 明确失败，不消费 Y；保存原门槛和 POISONED/保留所有权语义；优先离线注入 |
| BEGIN/END 写入、短写、fsync 失败、文件替换、崩溃中断 | 开始失败不提交，结束失败不假成功；缺 END 的请求恢复不自动重放；日志有界 |
| 严格/普通切换与回退 | 只在安全空闲边界切换；无活动授权跨模式复用；旧证据仍可按原版本复现 |

### 8.2 两套耗时指标

**整窗指标**：准备/校验、加载、预热、完整数值采集、原件核对/传输、普通性能样本、关闭恢复、报告登记分别记录；给出完整 wall time。一次性取证移出性能窗口后，不能从版本总成本中消失。

**请求指标**：从应用接收文本前计到原生首 token 的 TTFT_app；另列 prefill、decode、生成结束、内容核验完成，以及 END 持久化后的最终交付时间。原生 token 事件是内部测量点，不绕过现有内容检查直接交付用户。

固定模型/核/输入 token/输出策略/线程/微批/驻留/缓存/诊断开关。先每组 5 次筛查，再对最终候选至少 30 次热请求配对，以 A/B、B/A 交替；这是建议测试设计，未执行。报告中位数、范围、失败率和原始样本，不用 30 次声称稳定 p99。冷启动及持续稳定性另测，发生失败保留全部样本。

计数至少包括许可 IPC 次数/等待、fsync 次数/等待、健康采样与最大新鲜度、显式 BO 分配、实际提交及已验证完成、最低采样 CMA/内存、监控成本和故障响应延迟。父子计时不可重复相加；后台监控成本仍记录。日志和健康细计时尽量累加于内存，不为测开销新增逐投影落盘。

建议工程目标：无逐投影 fsync、无逐投影健康文件扫描；微批模式无逐投影许可往返；正确性及故障门禁不退化；完整交付延迟可重复改善。许可等待占 prefill 低于 2% 可作探索目标，同时报告绝对毫秒；它不是当前已承诺指标。

| v3 重型诊断 prefill，非普通应用 TTFT | 完整 R0 | 前缀命中 |

| 项目 | 当前验收阶段 | 稳定使用阶段的目标 |

| 健康保护 | 为定位和验收频繁采集，逐投影新鲜检查 | 有界周期监控+事件即时锁存+启动前快照检查；异常仍拒绝新任务 |

| 会话隔离与回答审核 | reset、前缀验证、事实/单位/肯否检查 | 这些继续逐请求执行；不会因调试轮数多而取消 |
| 平台恢复 | 每个独立维护/验收窗口关闭并恢复 | 同一受控服务生命周期持续持有设备；正常退出/维护才释放和恢复，禁止跨请求抢占 |

这种转变减少了实验取证、反复初始化和重复管理，用户更快得到回答，日志体量和资源扰动更小。**多轮调试本身不会自动启用这些变化**：必须实现并验收对应模式；安全关口、数值/内容质量、性能达标、真实故障恢复分别满足要求。现存教师审核、TT10 普通 PL 性能和未覆盖硬件故障不能因“准备投入使用”被补记为通过。
