# A12 有界常驻交互服务：无板接线设计（2026-10-26）

状态：设计，尚未实现、尚未验收。当前代码仍为三请求验收窗。本设计是后续无板接线依据，不是计算、上板、恢复或释放授权。

目标是把输入送入已经就绪的模型，得到经过原内容检查、END/回执持久化和最终新鲜检查的答案。当前事实句候选在旧CPU验证器通过25项；私有协议当前代码的全量复验仍在进行。不能将这些内部计时直接当作最终用户输入端到端或Board性能。

## 1. 生命周期与界限

- 同一受控父进程持有原Owner/租约/双锁并创建native；CPU和Board provider保留明确类型边界。Board factory仍要求真实注册root ARM64和原Owner，不提供JSON批准、PC覆写或隐式回退。
- 启动阶段复用原资产/模型完整SHA、完整待分配BO准入、driver/IRQ/拓扑及live-source门禁；取得READY、72权重常驻及34-token公共中立前缀的完整warm END/回执后，才给应用ready。
- 单实例最多1次warm和8次模型请求；总启动预算仍为5000，不按请求退款或重置。每次请求先检查“累计已消耗+本次最坏预算”能否容纳，另检查原4096行/4MiB日志、stdout/回执容量；不足时在BEGIN和发送之前拒绝。不得以预计提前EOS作为资源保证。
- 保留实际租约期限和原服务窗口上限1800秒；CPU测试期限必须显式冻结。不得延长现有Owner租约或修改原上限。期限/健康故障后不进入新请求，不把重新创建对象当作刷新权限。
- 只在实际已知空闲且显式关闭时完成native关闭握手。Board正常native结束进入等待原Owner恢复/finish；故障仍保留unknown、撤销页、DIRTY和所有权，不自动恢复、释放或重放。

这是一段有界常驻服务生命周期，不承诺无限连续服务。达到预算/期限后如何取得下一合法窗口属于独立的原Owner编排；不通过悄悄重置native累计计数来维持表面在线。

## 2. 应用与请求身份

- 接入原Session/planner/病例版本/转录来源检查。只允许已确认输入进入模型；原7项拒绝/澄清/低置信策略继续零模型调用。原始问题留在应用审计和请求身份中，不再次交给事实句生成提示词解释。
- 只有原planner选定的已核对事实句进入新提示词。原有限内容checker、单位/数字/肯否/未知、原自然EOS、状态清理及输出限额继续生效。模板兜底不能记为模型回答成功，医学/教师审核保持独立未完成。
- 维护有界去重表和单一活动请求；输入ID与内部native序号分离。warm及后续模型请求采用预定、无路径含义的唯一内部ID，回执文件不能复用。重复输入ID、活动期第二请求、非法病例/来源均在发送前拒绝。
- 同一公共前缀只包含中立指令和固定模板，不包含病例事实或用户问题。切换病例/会话仍清活动状态、核对case/plan，恢复中立前缀；不把上一病例状态或历史注入另一个病例。
- 输入到可交付回答计时从应用收到输入开始，包含路由/提示词渲染/分词、准入、实际计算、内容检查、END/回执和最终fresh fence。启动/warm单列，原生首token继续是内部事件，不绕过内容门槛直接交付。

## 3. 对现有私有管理链的必要变化

不修改B核、公共数学/ABI及现有冻结源码；使用A私有派生文件，逐项保存可逆变更和原SHA。

1. 从固定三请求列表改为可信应用逐次生成的有界请求；原请求wire摘要、Page.begin、T/尾块/full-plan、核启动/完成和图拷贝核验不变。
2. prefix身份绑定固定提示词策略、病例/检查器版本、模型/native/math/模板及允许输入模式。未来未知问题不伪装成已列举的冻结workload；每次实际wire仍单独BEGIN绑定。
3. typed CPU provider用现有真实数学；typed Board provider继承原门禁/Owner接口并使用匹配A53制品。CPU的逐字节logits/状态参考只用于PC验收，不能不经分析转为Board的数值容差规则；真实PL数值验收按原要求另行完成。
4. 日志回执从三个固定名称扩为上述有界内部ID集合，保留O_EXCL/NOFOLLOW、所有权、哈希链、短写/fsync失败锁存及容量。不得扩成任意文件名或无界集合。
5. native stdout界限按最多8个24-token输出及生命周期消息推导，仍保持单行及总字节硬限；不新增重型诊断或逐投影磁盘记录。
6. 正常关闭从“恰好完成3项”改为“无活动请求、已完成warm、所有实际请求已核验收口且显式停止”；原native正常exit0、持有pidfd终止、只读页无active/unknown及原Owner释放门禁保留。

## 4. 无板验收矩阵

| 项目 | 必须提供的证据 |
| --- | --- |
| 真正常驻 | 同一native PID/代次、一次72权重加载、一次中立warm，随后多个真实输入；加载不藏入请求计时或反复重做 |
| 应用交付 | 原25固定输入分有界窗口覆盖，原7策略项零模型；至少换病例、重复ID和两个连续真实输入；不筛失败 |
| 预算与容量 | 累计实际/最坏预算、尾块/提前EOS、硬上限前拒绝、日志/回执/stdout容量前拒绝；拒绝不自动重放或退款 |
| 私有协议 | 实际CPU调用/核验数与Page/GRANT/图拷贝一致；BEGIN前不提交；END/receipt失败、健康失败、取消及摘要错误不交付 |
| 健康与生命周期 | 旧代次和节点重建拒绝；持久I/O后的最后新鲜度符合原250ms；I/O期间故障锁存；未知/活进程不能宣告释放 |
| typed Board准备 | PC不能构造Board provider；固定根路径、原资产/BO/IRQ/lease/双锁门禁、Owner worker/finalization接口静态/PC代理验证，ARM执行继续NOT_TESTED |
| 性能范围 | 新应用入口到最终交付计时、冷启动/预热单列；样本和失败全保留；PC结果不转成A53/PL保证或p95 |
