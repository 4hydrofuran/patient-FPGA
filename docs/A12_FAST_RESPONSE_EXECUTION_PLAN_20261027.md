## 1. 目标、实现路线与成功口径

用户的根本目标是：**输入完一句话后，尽快看到真正可用的回答。** 优先减少每轮模型计算及等待时间，同时保持原病例事实、内容核验、评分、请求归属和正常关闭流程。

实施主线为：**保留已实板通过的连续网页问诊和NativePL，接入已在PC通过的facts-only短提示词，公共前缀由70改为候选34 token；模型和前缀在接收问题前准备完成。** 随后仅作必要的热路径整理和2/3线程小范围比较。

```text
启动：原Owner → 同一native worker与72份权重 → 短公共前缀预热 → 网页可接收问题

每问：原始输入/身份 → 原Session与planner → 本轮允许的完整事实句
      → 短提示词 → 已预热前缀命中 → 真实PL生成
      → 原内容/EOS/交付核验 → 已有SSE → 界面显示回答 → 原评分

结束一场：冻结该场评价；继续复用同一worker
停止服务：停止接收 → 处理在途请求 → 原Owner正常关闭/恢复 → 独立释放回执
```

本轮不训练模型，不更换量化、B核、xclbin或公共ABI，不引入另一套resident私有服务替换当前网页后端。已有resident候选可参考其提示词和验证经验，但其独立session/submit/ack协议不作为本轮主线。

| 指标 | 定义与目标 | 如何判定 |
| --- | --- | --- |
| UI接收反馈 | 提交后约0.3秒内出现已接收/处理中 | 仅体验反馈，不计作模型回答 |
| 内部首token | 原输入进入后端处理，到native产生第一个输出token；争取小于10秒 | 作为计算提速子目标，不等于已经显示核验答案 |
| 可见核验回答 | 浏览器提交本次问题，到当前问题的核验答案完成界面绘制；本轮争取15秒以内，继续争取10秒以内 | **用户体验的主要指标**；最终“10秒内应答”只按这一口径判断 |
| 功能与PL真实性 | 原内容/EOS、MODEL/FPGA_REAL、真实34-token命中、会话与评分正确 | 与速度分别记录，功能通过不自动代表速度达标 |

界面继续在原核验通过后显示模型回答。未核验token、加载提示或模板结果均不得计作成功模型应答。若未来希望逐字流式显示真实答案，需要单独设计可逐段成立的核验机制，不在本轮临时绕过检查。

### 2.2 收益的可实现范围

按8-token分组，新增37 token需要5组prefill；14～21 token需要2～3组。**此前7～11秒的估计指内部首token，不是完整网页答案。** 真实收益还受尾块、CPU部分、固定调度和检查耗时影响，需板测。

若同样短答案的decode仍约10.841秒，内部首token即使降到7～11秒，完整核验回答仍可能在约17～22秒量级。因此本轮将decode、线程配置与界面交付一并计时；不承诺仅靠缩短输入就能达到可见回答小于10秒。

同结构模型的普通继续训练不会自然减少每个token所需的前向计算。训练可帮助缩短指令或答案，但要重新验证内容、量化和板端效果，故不放入本轮验收前的关键路径。若本轮后仍明显受decode限制，再另议小模型蒸馏、结构压缩或计算实现优化。

```text

```

| 类型 | 限制与用途 |
| --- | --- |
| 普通短提示词配对探测 | 5000次/1800秒、72次权重；独立派生包，输出24，按冻结请求算账，不改原普通包 |


题目和顺序无板时冻结。浏览器实测提交到答案绘制，后台记录同一请求的内部TTFT、prefill、decode、完整核验；列出输出token数，避免把短答案和长答案混为同题提速。
